# Release 0.1.0-alpha.4

Alpha.4 separates two questions: whether a Windows test candidate was built and
checked correctly, and whether that exact candidate passed live Relution tests.
Each build targets one approved qualification tenant. Its MSI remains unsigned
and cannot be distributed.

## Two build profiles

Set `APPPORT_QUALIFICATION_PROFILE` to `read_only` or `write_qualification` when
building the client. `APPPORT_RELUTION_WRITES_ENABLED` must match: `false` for
read-only testing and `true` for write testing.

Release builds require `APPPORT_QUALIFICATION_TENANT_APPROVED=true` and
`APPPORT_RELUTION_TENANT_CLASS=qualification`. The write profile also requires
`APPPORT_DISPOSABLE_RESOURCES_APPROVED=true` and a separate, non-secret plan naming
the disposable resources used for testing. Keep that plan out of the repository
and release evidence.

## Candidate checks and live results

`candidateReady=true` requires a clean source tree, passing source checks, a
Windows MSVC MSI and its SHA-256 hash, valid embedded configuration, and a passing
secret scan. It also requires installing the MSI, passing its self-check, and
uninstalling it afterward. The report records `signed=false` and
`distributable=false`.

`pilotQualified=true` requires a separate approved live test of that candidate
using its selected profile. Passing the build checks does not imply a successful
live test. Any managed-device or deployment tests that have not run remain
outstanding.

## Test scope

Tokens are entered only at the qualification utility's masked console prompt.
They must never appear in arguments, environment variables, files, logs, or
reports.

Tests may uninstall the Appport MSI as part of cleanup. They do not cover
uninstalling applications through Relution, administrative actions, or production
use. Signing and publication require a separate release decision.

## Changes before live qualification

These changes were made after the October 2026 readiness review, before any
alpha.4 candidate was qualified:

- An action whose result is `unknown` no longer locks the application forever.
  A status check confirms it from inventory when the exact package and version are
  installed. After 15 minutes, if Relution lists no matching active action, the
  action becomes `failed` with `UNKNOWN_RELEASED` and the application can be
  requested again. The client offers a **Check status** button for these actions.
- Every failed native command is written to the client log with a timestamp, so a
  support bundle shows what failed and when.
- `pnpm verify:source` prints the output of each failed check.
